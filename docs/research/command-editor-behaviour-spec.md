## 2a. Source study (ST-104-5; EZF-21 decision §3.1–3.2)
Method: `git clone --depth 1 --branch <tag>` into a scratch directory outside the Nexus repo, `grep` plus reading the parser and handler files; no build, install or run. Everything below is paraphrase; no code from these projects is in Nexus. Paths are relative to each repo at the pinned commit in §1 (S14–S17). Line numbers refer to that commit. Read date for all four: 2026-11-10. None of this verifies runtime behaviour: nothing was executed.

**WezTerm (S16, MIT, `5046fc22`)**
- Q1 boundaries: parses OSC 133 only (code mapping `termwiz/src/escape/osc.rs:439`, dispatch `:326-327`, parser `:670-754`). Handles `L`, `B`, `I`, `A`, `C`, `D`, `N`, `P` (`:683-685`, `:701-748`); reads `aid`, `cl` (`A`, `N`), `aid` (`C`, `D`), `k` (`P`) and the `D` exit status. The terminal core turns them into a per-cell semantic type Prompt/Input/Output on the pen (`term/src/terminalstate/performer.rs:845-886`); `D` changes no state (`:882-884`). Zones are derived from cell runs (`term/src/terminalstate/mod.rs:2695-2740`). There is no block object and no command text; OSC 1337 is used for user vars and cwd (`docs/shell-integration.md:4-5`). The shipped shell script emits `P;k=i`, bare `B`, `D;<status>;aid=<pid>`, `A;cl=m;aid=<pid>`, `C;` (`assets/shell-integration/wezterm.sh:472-493`).
- Q2 forgery: no distinction. Any byte stream that reaches the parser sets the semantic type, and the `aid` the script sends is the shell pid (`wezterm.sh:481,484`), not a secret. Search terms with no relevant hit: `nonce` (`term/`, `termwiz/`), `trust`, `forg` (`performer.rs`). No rate limit found.
- Q3 tmux: supports tmux control mode only: DCS `1000p` switches the parser to a tmux control-mode parser (`termwiz/src/escape/parser/mod.rs:247-249`), and `%output` text is written into the pane's terminal (`mux/src/tmux.rs:94-103`), so OSC 133 inside the pane is parsed as normal output. No handling of `allow-passthrough` found (search `allow-passthrough`, `allow_passthrough`, `Ptmux`; the only `Ptmux` uses wrap WezTerm's own outbound user-var and image escapes, `wezterm.sh:442`, `wezterm/src/main.rs:677`).
- Q4 unknown parameters (**mandatory**): for `A`, `C` and `D`, extra `key=value` parameters are collected into a map and unknown keys are ignored (`osc.rs:687-699`, `:701-748`). A non-empty parameter without `=` makes the whole sequence fail with `malformed FinalTermSemanticPrompt` (`:696`), and an unrecognised first parameter fails with `invalid FinalTermSemanticPrompt` (`:749-753`). **`B` and `I` are accepted only as exactly `133;B` (no further fields)** (`:683-685`); `133;B;nonce=…` is not matched by that shortcut and falls through to the final `bail!` at `:749-753`, so WezTerm drops it and does not enter the Input zone. The `D` status is read from the first field after `D` (non-numeric becomes 0), extra fields start at the third (`:690`, `:717-723`).

**Ghostty (S17, MIT, `83fb9562`)**
- Q1 boundaries: parses OSC 133 `A`, `B`, `C`, `D`, `I`, `L`, `N`, `P` (`src/terminal/osc/parsers/semantic_prompt.zig:23-32`, `:327-406`) and reads `aid`, `cl`, `k`, `err`, `cmdline`, `cmdline_url`, `redraw`, `special_key`, `click_events` and the `D` exit code (`:77-141`). `Terminal.semanticPrompt` moves the cursor's semantic content between prompt, input and output (`src/terminal/Terminal.zig:2156-2270`, `Screen.cursorSetSemanticContent` `src/terminal/Screen.zig:3021`); `N` is treated as `A` and `D` only resets to output (`Terminal.zig` same range). Blocks are not tracked ("We don't currently do explicit command tracking"), only prompt-line marks for jumping and click-to-move. The shipped bash script emits `P;k=i`, bare `B`, `D;<status>;aid=<pid>`, `A;redraw=last;cl=line;aid=<pid>`, `C;` (`src/shell-integration/bash/ghostty.bash:145-146,177,188,219`; zsh `src/shell-integration/zsh/ghostty-integration:116-124`).
- Q2 forgery: none found. Search terms with no relevant hit: `nonce`, `forg` (`src/terminal/osc`, `Terminal.zig`, `stream_terminal.zig`). `aid` is the shell pid. No rate limit found.
- Q3 tmux: tmux control mode only, DCS `1000p` (`src/terminal/dcs.zig:54-73`), compiled in only when the build option `tmux_control_mode` is on (`src/terminal/dcs.zig:55`; the option is set in `src/terminal/build_options.zig:296`, from the `oniguruma` flag). Pane `%output` is fed to a per-pane terminal stream (`src/terminal/tmux/viewer.zig:1141-1153`), so OSC 133 in the pane is parsed as usual. A code comment there says the control-mode stream can be written to by any program running in the terminal (`viewer.zig:1161-1163`), i.e. entering control mode is itself forgeable from output. Search for passthrough handling (`passthrough`, `allow-passthrough`) found only the generic DCS state machine.
- Q4 unknown parameters (**mandatory**): the parser keeps everything after `133;<cmd>;` as an unvalidated option string (`semantic_prompt.zig:327-406`); each option is read by key, and unknown or malformed options are ignored by design (comment `:15`, `:149-150`; reader `:151-215`). This holds for `A`, `B`, `C`, `D`: `B;nonce=…` is accepted. Only a letter immediately followed by something other than `;` is rejected (tests `:423-430` `133;Cextra`, `:1182-1189` `133;Dextra`; `133;C;aid=foo` is valid, `:432-442`). A value containing `=` is kept whole (`:785-792`).

**Wave (S14, Apache-2.0, `97e56002`)**
- Q1 boundaries: does **not** parse OSC 133, 633 or 1337. The xterm.js parser has only three OSC handlers registered, 7, 52 and 16162 (`frontend/app/view/term/termwrap.ts:184,192,200`). Boundaries come from Wave's own OSC 16162 with a `;`-separated JSON payload (`frontend/app/view/term/osc-handlers.ts:284-377`): `A` = prompt ready and registers an xterm marker (`:308-322`), `C` = command start with base64 `cmd64` command text (`:325`, `handleShellIntegrationCommandStart` `:98-130`), `D` = exit code (`:348`), `I` = input empty (`:356`), `M` = shell metadata (`:328`), `R` = reset (`:361`). The shell scripts emit these from a bash-preexec/zsh hook, capping command text at 8192 bytes (`pkg/util/shellutil/shellintegration/bash_bashrc.sh:88-111`; zsh `zsh_zshrc.sh:83-109`).
- Q2 forgery: none. The payload is plain JSON from the byte stream, with no secret (search terms `nonce`, `token`, `trusted` in `osc-handlers.ts`: no hit). The only guard is `loaded`, which ignores 16162 while the saved scrollback is being restored (`osc-handlers.ts:286-288`, set at `termwrap.ts:430-440`): replay protection on reload, not authentication.
- Q3 tmux: the shell integration turns itself off inside tmux/screen: `_waveterm_si_blocked` tests `$TMUX`, `$STY` and `$TERM` (`bash_bashrc.sh:59-61`, used at `:76,83,99`; `zsh_zshrc.sh:29-31`, used at `:73,80,98,116`; fish `fish_wavefish.sh:16-17`). So no blocks inside a multiplexer: fail closed, no passthrough. The UI also lists multiplexers as always-raw (`frontend/app/view/term/shellblocking.ts:5-7`). Wave has its own durable-session feature instead of tmux (UI text `frontend/app/onboarding/onboarding-durable.tsx:72`; not studied further).
- Q4 unknown parameters: not applicable to OSC 133, because Wave registers no 133 handler. For 16162 the analogue is: malformed JSON is logged and the command still runs with empty data (`osc-handlers.ts:293-302`), and unknown JSON keys are ignored because fields are read by name (`:328-347`). How xterm.js treats OSC 133 when no handler is registered is not tested here `[UNVERIFIED]`.

The only OSC handling in the session middleware is OSC 1337 `CurrentDir=` and OSC 52; every other OSC, including 133, is passed through to xterm.js unmodified (`tabby-terminal/src/middleware/oscProcessing.ts:66-84`). **Implications for BR-12 and BR-15.**
(1) Prior art: none of the four authenticates markers, so "OSC 133 has no nonce" is now a cited finding for these four, and the nonce remains Nexus's own hardening (BR-12 keeps the `[INFERENCE]` tag only for "nearest prior art is VS Code 633;E"). (4) Wave's `loaded` gate (ignore markers while replaying saved output) is useful input for BR-11/BR-15 reattach and is recorded for the ADR, no BR change. (5) Tabby's unbounded pending-OSC buffer supports the existing BR-12 "bounds buffers" requirement.

## 4. Behaviour requirements (BR)
- BR-1 Click anywhere in a draft (incl. 300+ chars, soft-wrapped) places the caret there. Clicking never executes or modifies submitted blocks.
- BR-2 Enter submits when safe; Shift+Enter newline (configurable); multiline/elevated drafts require explicit Run/confirm.
- BR-3 Editor undo/redo are draft-local and do not touch the PTY.
- BR-4 Soft wrap is visual only; the submitted text has no inserted newlines.
- BR-5 Paste: strip/reject C0/C1 control and ESC sequences except \n and \t; normalise CRLF and lone `\r` to `\n` (a pasted `\r` is never sent raw because it would execute); flag (do not silently strip) bidi controls U+202A–202E and U+2066–2069, zero-width/invisible characters (U+200B–200F, U+2060, U+FEFF) and mixed-script homoglyphs (Trojan Source class); show raw preview with escapes and flagged characters made visible; never auto-run.
- BR-6 Byte-exact framing. Single-line draft: draft bytes + `\r` (Enter is `\r`, never `\n`). Multiline draft when bracketed paste is active: `ESC[200~` + draft (with `\n` between lines) + `ESC[201~` + `\r`. Because readline may emit `?2004h` before `B` (inference, unrun) and prompt content can inject escapes between `A` and `B`, the preferred source is the integration reporting paste capability in the BR-15 event log (an advisory, forgeable source: same-user processes and a compromised shell integration can write it, so a forged value can only cause wrong framing, and it never independently authorizes a privileged operation). **BR-2 is the real bound on a forged "on":** a multiline draft is never sent without an explicit Run/confirm, so a forged "on" cannot make anything run that the user did not confirm, and a forged "off" only turns bracketed paste into line-by-line confirmed sends. **When the event log drives state (BR-15, §5) the PTY-stream DECSET 2004 observation is not used at all:** the PTY stream and the event log are two asynchronous channels with no shared clock, so a 2004 escape at a byte position in the PTY stream cannot be matched to an `A`/`B`/`C` position in the event log (the same two-channel race as TC-21). Matching by position is therefore not attempted; the framing relies on (i) the event-log paste-capability field reported at `B`, and (ii) the per-shell, per-version TC-04/TC-25 results: a shell and version without a passing TC-04 row is treated as "unknown". The PTY-stream fallback below applies **only** to sessions with no event log (in-band markers, §5): the connector's parser tracks DECSET/DECRST 2004 **only from the PTY stream while in INPUT state (after `B`, before `C`)**, with the value reset to off at each `A`; output from RUNNING or PENDING state never changes it. If state is off or unknown, multiline drafts are sent line by line, each requiring confirmation. No `sh -c` wrapper, no quoting changes. Any `ESC[201~` in the draft is removed under BR-5 before framing. **Executed-bytes invariant (B6/B7, see BR-16):** the bytes the shell executes for a submission equal the confirmed draft, even if keys were forwarded raw in PENDING, RUNNING or UNKNOWN since the last INPUT. In R1 this holds because **no draft is submitted, and no draft can exist, while the typeahead flag of BR-16 is set**; the connector never prepends a line-kill or reset prefix to the framing above, so the framing is exactly the bytes listed here.
- BR-7 One long-lived PTY; `cd`/exports persist across submissions.
- BR-8 Block = {id, command, cwd, host/user, start, end, exit code, output cursor}. Block boundaries come only from the BR-15 event log when it is active (§5), and otherwise only from nonce-verified OSC 133 markers emitted by Nexus's opt-in integration; output text can't forge either (see BR-12).
- BR-9 Block actions: Copy command, Copy output, Edit as draft (never auto-run), Rerun (confirm if destructive or cross-host), Share redacted, attach to issue.
- BR-10 Unknown shell / no markers → block grouping disabled, editor falls back to raw PTY with manual toggle.
- BR-11 Unsent draft survives disconnect/refresh and is never auto-submitted after reconnect.
- BR-12 Marker nonce `[INFERENCE: OSC 133 has no nonce; VS Code's OSC 633;E nonce (S10) is the nearest prior art]`. The integration puts a random nonce (>=128 bit, CSPRNG) in each marker's params; the parser drops markers without the valid nonce, bounds buffers, and rejects unknown OSC from untrusted output for HTML/links. The nonce is a shared secret against passive content only; it is not a cryptographic authentication of the shell (see BR-15 for what can forge).
  - Defends against: passive content (`cat`, `curl`, logs, MOTD, file contents) that does not know the nonce.
  - Does NOT defend against: programs the user runs as the same OS user that can read the shell environment, the nonce file before it is deleted (residual risk below), or earlier terminal output; nor a compromised shell integration.
  - Required: (a) nonce held in a **non-exported** shell variable (never in the environment of children; verify `env` and `/proc/<pid>/environ` of a child lack it; note `set` in the same shell can print it, so the integration unsets/hides it from `set` output where the shell allows, else documents residual risk); (b) the connector strips nonce-bearing marker bytes from rendered output, scrollback, block records, shared/redacted output and Paperclip attachments;
  - (c0) **Initial nonce delivery, outside the PTY.** Two separately authorized, **fixed** SSH operations exist, never free-form exec: **(1) read-only** access to the session event log (BR-15); **(2) a write-once operation that delivers the initial nonce file and creates the empty events file (below).** Both enforce the **same** session identity, role authorization, auditing and revocation rules (TELEPORT_IDENTITY_ACCESS; revocation via NX3-111) and are revoked together with the session. The **connector** generates the nonce with a CSPRNG (>=128 bits) and delivers it only through operation 2; it is never typed into the PTY (it would echo into scrollback, tmux history and `tmux capture-pane -S -`). The **receiving helper** (a fixed, Nexus-supplied command, not a shell) creates `$XDG_RUNTIME_DIR/nexus/<session>/nonce` (fallback `~/.cache/nexus/<session>/nonce`) **atomically with exclusive create (`O_CREAT|O_EXCL`) and mode 0600**, owned by the remote login user (the same user as the shell), inside the session directory created with mode 0700 and the same owner, and **rejects any overwrite** (file already exists ⇒ operation fails, is audited, and the session start is aborted). **In the same operation 2 the helper also creates the empty events file `…/<session>/events` with `O_CREAT|O_EXCL` and mode 0600** (same owner, same 0700 directory); the file is created before the shell starts, by the helper and never by the integration, so there is no create race and no umask dependence. The **shell integration** reads the nonce file into the non-exported variable and **deletes it at initialization**; it opens the events file only for append (never creates it, so a missing events file means no events).
  - **Initialization ordering:** (i) connector authorizes the session; (ii) helper creates the 0700 session dir and, via operation 2, the 0600 nonce file and the 0600 events file; (iii) only then the connector starts or attaches tmux and launches the shell (`new-session`/`new-window`) so the shell's rc sources the integration; (iv) the integration reads and deletes the file before emitting its first `A`; (v) operation 1 begins reading the event log. The file therefore exists before the integration reads it. **If the file is missing, unreadable or already consumed at initialization: no nonce ⇒ the integration emits no markers and writes no events (with no nonce there is no side channel either), the connector's state is UNKNOWN (§5), no draft is captured (BR-16) and the editor is in raw PTY mode;** the connector never falls back to a nonce-less or PTY-delivered nonce. On reattach the integration is already initialized and the connector reuses its stored nonce; operation 2 is not repeated for a live session.
  - **Extra shells in a live session fail closed.** A shell started later in the same session (new tmux window or pane, `exec $SHELL`, `su -`, `sudo -i`) finds no nonce file (it was consumed at the first initialization and is not in the environment), so its integration has no nonce: it emits no markers and writes no events, the connector sees no valid state for it and stays UNKNOWN / raw PTY with no draft capture (BR-16). Giving such a shell its own nonce needs a new operation 2 for a new session; it is not done for a live session in this release.
  - **Teardown** deletes the whole session directory (`…/nexus/<session>/`), including an unconsumed nonce file (for example when the shell never started), the events file and any partial files; to be verified by TC-12.
  - **Residual risk (c0):** between file creation and deletion, other processes running as the same OS user can read the file (0600 does not protect against the same uid); the window is bounded by shell start-up, and a nonce obtained that way lets such a process forge markers. Same-user processes can forge anyway (BR-15), so this is accepted and documented, not mitigated.
  - (c) **Rotation: per session only for the initial release.** A new session gets a new nonce through operation 2. A new nonce is **never** transmitted in `D` or in any other PTY output, and there is no in-band or side-channel rotation. Per-prompt rotation needs further design and testing and is recorded as a separate proposed ADR: `docs/adr/ADR-PROPOSED-per-prompt-nonce-rotation.md` (status: Proposed – needs design and testing). (e) **Wire format (from the ST-104-5 source study, §2a Q4).** The nonce rides as a `nonce=<hex>` key=value option on `A`, `C` and `D` only; `P` is not emitted by the Nexus integration and carries no nonce. For `D` the form is `133;D;<status>;nonce=<hex>` (exit status first, because both studied parsers read the status from the first field after `D`: WezTerm `osc.rs:690,717-723`, Ghostty `semantic_prompt.zig:168-175`; `D;nonce=…` would make WezTerm report status 0 and Ghostty none). `B` is emitted **bare** (`133;B`): WezTerm drops any `B` that carries a parameter, while Ghostty ignores unknown options on all four marks, and both ignore an unknown `key=value` on `A`/`C`/`D` (kitty is not source-studied; S4 docs only, so TC-10/§10 item 6 still require a local check). Because `B` carries no nonce, an in-band `B` is accepted only immediately after a nonce-valid `A` in order, and any other `B` ⇒ UNKNOWN (TC-10). When the event log drives state (BR-15) in-band markers are not used for state at all, so this affects only sessions without an event log and terminals that show the markers locally. (d) a marker with the wrong nonce is ignored and logged (replay of a nonce leaked from earlier output within the same session is not detected in this release; it is covered by the residual-risk statements above).
- BR-14 Terminal response-injection class. OSC 52 clipboard **read** is always denied; OSC 52 **write** is off by default and requires per-session user consent. Responses to queries (DA/DSR/CPR, `CSI 21 t` title report, DECRQSS, OSC 10/11 colour queries) must never contain attacker-controlled bytes (titles, text from the stream) and are generated only by the terminal core, never echoed from output into PTY input; `CSI 21 t` is not answered. OSC 0/2 titles are stripped of C0/C1 controls, length-capped and rendered as text only.
- BR-15 tmux. Nexus sessions run in remote tmux (SESSION_PERSISTENCE.md §1). OSC 133 inside a pane is not relied upon to reach the client: per S11/S12 it may not work, and forwarding needs `allow-passthrough on` which lets any pane program emit arbitrary escapes to the outer terminal (and tmux can undo passthrough state, S12). `[S13: tmux 3.4+ consumes OSC 133 for prompt navigation, 3.7a fires hook events from it, so tmux hooks are driven by pane-stream bytes and passive content (`cat evil.txt`) can forge them: record in ADR comparison. UNVERIFIED-LOCAL: forwarding to the client and older versions dropping it; no tmux/container runtime exists in this run's sandbox, so TC-21 must confirm.]` **Proposed decision:** `allow-passthrough off` (default); the shell integration inside the pane writes block events (A/B/C/D + cwd, exit, command id, sequence number) to a **side channel**, a per-session append-only file under the 0700 session dir (`$XDG_RUNTIME_DIR/nexus/<session>/events`, fallback `~/.cache/nexus/…`) read by the connector through the read-only fixed SSH operation 1 of BR-12(c0). Block records therefore do not depend on the pane byte stream. On reattach, tmux redraws the screen without markers; blocks are rebuilt from the event log (with a stored byte offset per block into a connector-side output ring, or marked "output unavailable" when the ring has expired), not from the redrawn screen. Alternatives if the side channel is rejected: tmux hooks (`pane-*`/`alert-*`) plus `pipe-pane`, and tmux control mode (`-CC`), which is what WezTerm and Ghostty support (§2a Q3); in control mode pane output is still parsed in-band, so a forged marker in output still reaches the parser, and entering control mode is itself triggered from the output stream. To be compared in the ADR. No studied project (§2a) ships a side channel; Wave turns its integration off inside tmux/screen, which is the fail-closed behaviour Nexus also applies to extra shells (BR-12). **State source:** when the side channel is active the §5 state machine is driven by the event log only (§5, BR-16); BR-15 stays *proposed* until TC-21 results exist.
  - **Integrity model (no cryptographic authentication).** Events carry **monotonic sequence numbers**, which detect **gaps and reordering only**. There is no HMAC or other MAC: the writer (the shell integration) cannot compute a MAC under a secret it does not hold, and one it holds would be readable by same-user processes. Events are **not cryptographically authenticated.** Same-user processes and a compromised shell integration **can forge events** (including valid sequence numbers), and **event data never independently authorizes a privileged operation** (e.g. it cannot by itself approve Run, elevation, Rerun, sharing or a redaction bypass; those need the user action or policy check on the connector side).
  - **Ownership and permission controls:** the events file is owned by the remote login user, mode 0600, in the 0700 session dir (same owner), **created by the helper with `O_CREAT|O_EXCL` as part of operation 2, before shell start** (BR-12 c0), append-only by the integration (which never creates it); terminal output cannot write files, so passive content (`cat evil.txt`) cannot forge entries, which is the protection (write access control, not cryptography). Other OS users are excluded by mode; the same user is not.
  - **Secret-persistence:** the log holds `cmdline` and cwd, so it is a secret-persistence site: deleted on session end (and by the connector on teardown, which removes the whole session directory including any unconsumed nonce file), bounded retention while the session lives, and cmdline/cwd are redacted by the connector's redaction pipeline before the connector stores or forwards anything; the log is included in TC-07's canary grep. The BR-12 nonce never touches the log.
  - **(c) Fixed SSH operations:** operation 1 (read-only tail of the events file) and operation 2 (write-once nonce delivery, BR-12(c0)) are two separately authorized fixed operations, never free-form exec; both use the same session identity, role authorization, auditing and revocation rules as the PTY (TELEPORT_IDENTITY_ACCESS; revocation / reattach authorization: NX3-111), with the connector-generated CSPRNG nonce delivered only through operation 2.
- BR-16 Input routing. State machine of §5 gates all input: only in INPUT (after `B`, before the submission) are keystrokes captured into the draft. **Submission leaves INPUT immediately:** on Enter or Run the connector sets PENDING at once, locally, without waiting for `C` (which arrives later over the event log, with the op-1 latency), and PENDING is treated exactly as RUNNING for input. It records `submit_seq` = the highest event sequence number it has seen at that instant. Return to INPUT happens **only on a `B` whose sequence number is greater than `submit_seq`** (and in order after the intervening `C`/`D`/`A`, or after an `A` alone: an empty or comment-only submission may yield `A`→`B` with no `C`/`D`, because bash-style integrations emit `D` only if preexec ran, `wezterm.sh:479-481`); a `B` with a lower or equal number (including a delayed copy of the current prompt's `B`) is ignored. In PENDING, RUNNING (after `C`, before `D`) and in any state where markers are missing/UNKNOWN, keystrokes go straight to the PTY and are never captured into the draft, history, suggestions or AI context. In PENDING/RUNNING/UNKNOWN Ctrl+C is delivered as `0x03`, Ctrl+D as `0x04`, Ctrl+Z as `0x1a`, never intercepted by the editor. In INPUT with a **non-empty draft**: Ctrl+C clears the draft and sends no `0x03`; Ctrl+D deletes the character under the cursor (or asks for confirmation) and sends no `0x04`, so the shell is not logged out. In INPUT with an **empty draft**: `0x03` and `0x04` are delivered raw (`0x04` after confirmation) (see TC-26). The editor's own copy shortcut uses Ctrl+Shift+C / Cmd+C. **Typeahead isolation (B6, B7): fallback-only for R1.** Invariant: *the bytes the shell executes for a submission equal the confirmed draft, even if keys were forwarded raw in PENDING, RUNNING or UNKNOWN since the last INPUT.* Raw-forwarded keys that the running command does not read stay in the tty input queue and the next prompt's line editor reads them into its line buffer, where the draft editor cannot see them (the editor must not import that line into the draft: that is the B5 defect, which would capture secrets). **Mechanism, chosen (rev 7): no kill prefix is ever sent.** The connector keeps a **typeahead flag**:
  - **Set** by *any* byte forwarded raw since the last INPUT, counted over the whole span (PENDING, RUNNING, UNKNOWN, and raw keys sent in INPUT or in the typed-ahead state itself), not only the bytes after the last forwarded `\r`: what the running program consumed cannot be observed, so the content of the span is not inspected at all.
  - **Cleared only by one route:** a `B` whose sequence number is greater than the `clear_mark` and with **no byte forwarded raw after the clearing key**, where the clearing key is a raw `\r` (Enter) or raw `0x03` and `clear_mark` is the highest event sequence number the connector had seen when that key was forwarded. Reading: the user pressed Enter or Ctrl+C in the terminal, the shell finished with its old line and drew a fresh prompt, and the user typed nothing since. The same rule covers the Enter and Ctrl+C that leave INPUT raw (a raw `0x03` in INPUT with an empty draft, a raw Enter in the typed-ahead state, and the new `B` that follows). A raw byte forwarded after the clearing key sets the flag again (keys typed in the typed-ahead state are raw and set it), and the clearing key must be repeated.
  - **While the flag is set the editor is in the visible raw "typed-ahead" state** ("shell line may contain typed-ahead text"): it behaves as UNKNOWN (no capture into draft, history, suggestions or AI context; keys go straight to the PTY; BR-2 never sends anything the user did not confirm because there is no draft). Because no draft can be submitted in this state, the connector never has a submission to prefix, and nothing has to be reset, killed or expanded by Nexus.
  - **Why fallback-only (decision record).** Three review rounds in a row found a new edge in a connector-sent line-kill prefix. The C1 probe (bash 5.2.37, EZF-30) showed that `0x05 0x15` after raw-forwarded typeahead is read in the line editor's current state: after `ESC` it is M-C-e `shell-expand-line` (a `$(…)` in the typeahead ran), after `C-x` it is `edit-and-execute-command` (the typeahead line was executed), and in vi command mode it ran `o DRAFT_Xc` instead of the draft. A user's `inputrc`/`bindkey` may also rebind `C-e` or `C-u` `[INFERENCE]`, and zsh/fish were not probed. The connector cannot see the line editor's pending key sequence or keymap, so any prefix that is *sent* can be wrong; a typed-ahead byte that is *not touched* by Nexus cannot be executed or expanded by Nexus. **B7(a) is met trivially and B7(b) is not needed in R1:** the eligibility rule is "no raw byte since the last INPUT", so no binding check and no per-shell, per-edit-mode prefix table exist; there is nothing to forge (the shell and edit mode are not consulted). The kill-prefix and reset optimisation is moved to the proposed ADR `docs/adr/ADR-PROPOSED-typeahead-line-kill-prefix.md` (status: Proposed – needs design and the TC-04 matrix before it can be enabled).
  - **UX cost, stated plainly.** After *any* raw keystroke since the last INPUT the smart editor does not return until the user clears the line in the terminal with Enter or Ctrl+C. This includes keys the user typed into `vim`, `less`, `top`, `apt` Y/n, a `python3` REPL, a `sudo` password prompt, a stray Esc or a key typed during the op-1 latency window, even though in many of those cases the shell line is in fact empty. The flag over-sets by design; one extra Enter per such command is the price of having no connector-sent bytes that can be misread. An Enter on an empty shell line is harmless; the typed-ahead text, if any, is then run or discarded by the user's own raw action in the terminal, outside the draft path and outside what Nexus confirms or records.
  - **In-band sessions (no event log, N9).** The fallback needs no shell or edit-mode report, so it behaves identically: the flag is Nexus's own bookkeeping of raw forwarding, and the clearing `B` is the in-band `B` that follows a nonce-valid `A`, numbered in arrival order (§5). No other source is needed. (Under the proposed ADR, a session without an event log has no source for shell and edit mode and would always stay on the fallback.)
  - **Discarded keys:** Nexus does not read, kill or inject anything into the typed-ahead text; it is never stored in the draft, history, logs, event log or AI context, and the editor shows only the one-line state label (no content). Typeahead that contained a newline was already executed by the shell as its own command before the next prompt, outside the draft path.
  - **Residual: shell kill ring (N10) `[INFERENCE]`.** readline `unix-line-discard` and zle `kill-whole-line` save killed text in the shell's own kill ring, so `C-y` in raw mode can yank it back. This is read from the readline/zle docs and not tested. In R1 Nexus never sends a kill, so the residual arises only if the *user* presses Ctrl+U or Ctrl+K in the typed-ahead state (a typed-ahead secret could then sit in the shell's kill ring); that kill ring is shell memory, outside every Nexus store and outside TC-07's grep scope. It is recorded next to the sudo-canary case in TC-07b. If the proposed ADR is adopted, a connector-sent kill would make this residual unconditional and the ADR must address it. "Never stored" means in Nexus's stores only.
  - **Why this and not a flush:** a tty input flush (`tcflush`) needs a second privileged write path and races with the PTY.
  This covers `read -p`, `apt` Y/n, `python3` REPL, `cat` waiting on stdin, and `sudo`/`ssh`/`su`/`mysql -p` secret prompts.

## 5. OSC 133 marker model (S4; S8 to confirm)
`A` prompt start → `B` prompt end/input start → `C` output start (command executing) → `D;<exit>` command end. kitty options: `k=s` (secondary prompt/PS2), `cmdline`/`cmdline_url` (S4); `aid`, `cl` `[UNVERIFIED: S8]` (not in S4). State machine: `PROMPT(A) → INPUT(B) → [submit] PENDING → RUNNING(C) → PROMPT(D→A)`, where PENDING is entered by the connector itself on Enter/Run, is routed like RUNNING, and leaves only to INPUT on a `B` with sequence number > `submit_seq` (BR-16); a `C` or `D` arriving in PENDING advances it to RUNNING/PROMPT as usual. If the shell never produces a new `B` (command hangs, shell exits) the state stays raw; the user toggle and "Reset prompt detection" (§6) remain available. **Which source drives the machine:** when the side channel is active (a nonce was delivered and operation 1 is reading the BR-15 event log) the state machine is driven **only by the event log** (sequence-numbered events); OSC 133 bytes in the PTY stream are not used for state and are still stripped from rendering. In-band nonce-validated markers (BR-12) drive it only for a session with **no** event log; in-band markers carry no sequence numbers, so the connector numbers them in arrival order, and PENDING exits only on a `B` that follows a nonce-valid `A` received after the submission. The two are never mixed, so a forged in-band marker cannot move an event-log-driven machine. **With no nonce the integration writes no events** (and emits no markers), so the state is UNKNOWN. The Nexus integration MUST always emit `B`; if `B` is missing the state is UNKNOWN and no draft is captured (BR-16), keystrokes go raw to the PTY. A missing initial nonce (BR-12 c0) likewise yields UNKNOWN. Duplicate/out-of-order markers ⇒ reset to UNKNOWN and drop grouping for that block. Shells: bash (via PROMPT_COMMAND/DEBUG trap — Warp notes bash needs preexec shim, S3), zsh (precmd/preexec), fish (events). Support matrix to be proven in tests.

## 6. Mode switching: SMART_INPUT ↔ INTERACTIVE_PTY
Safety is structural (BR-16): draft capture exists only in INPUT state. Everything below decides UX (editor visible vs hidden), not whether secrets are captured.
Enter INTERACTIVE_PTY when ANY: (a) DECSET 1049/1047/47 alt-screen set; (b) DECSET 1000–1006 mouse reporting on; (c) RUNNING for more than N = 500 ms `[INFERENCE: initial value]` with no `A`/`D` marker and the foreground command not known to be line-oriented; the prototype must measure false positive/negative rates over the TC-08/TC-22 command set (vim, top, less, apt, python3, read, cat, sleep, ssh) and adjust N; (d) UX hint only: output tail matches a password-prompt regex (`[Pp]assword|passphrase|Passwort|\[sudo\]`), which shows a "secret input" indicator; a non-match does NOT make capture unsafe; (e) user manual toggle (Ctrl+Shift+T, configurable).
Return to SMART_INPUT when: alt-screen reset AND next nonce-valid `A/B`; or user toggle; or "Reset prompt detection"; **and, in every case, only when the BR-16 typeahead flag is clear.** The "typed-ahead" raw state (any raw byte since the last INPUT, BR-16) is left only by the user's raw Enter or Ctrl+C followed by a new `B` with nothing typed in between (BR-16 clearing route); alt-screen reset alone, the user toggle and "Reset prompt detection" do not clear it, because none of them proves the shell line is empty. Expect this after vim/less/top and after any command that read keys.
In INTERACTIVE_PTY, PENDING and RUNNING: all keys incl. Esc, Ctrl combos, mouse and resize (SIGWINCH via PTY resize) go to xterm.js untouched; editor hidden or inert. Nested `ssh`, vim, nano, top, less, tmux-in-tmux, `bash -x`: raw. If detection is wrong, the toggle must remain reachable and never be captured by the app.
Nested ssh prints no nonce-valid markers from the inner shell ⇒ stays raw unless inner integration installed.
